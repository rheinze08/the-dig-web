# The Dig website — Phase 9C report: rating, keywords, contact, directions, calendar, favorites

Phase 9C of Roland's approved Phase 9 plan (Jenn's tester feedback; full plan in
rheinze08/the-dig as `PHASE9-PLAN.md`). Repo: rheinze08/the-dig-web. The site is
static, generated by `build.mjs` from the live feeds in rheinze08/the-dig-data
and served from `docs/` by GitHub Pages. Live site:
https://rheinze08.github.io/the-dig-web/

## The one fact that shapes this build

**The published feeds do not carry the Phase 9 fields yet.** At build time
(2026-11-21), the live city feeds on `rheinze08/the-dig-data/main` contain none of
`digRating`, `ratingReasons`, `photoKeywords`, `contentsLine`, `contactPhone`,
`contactUrl`, `photoCount` (verified directly against the raw feeds: 0 of 28
Houston sales, and `docs/build.json` records the same for all 207 sales sitewide).
Phase 9A has built those fields — its enriched output exists in the local
the-dig-data checkout — but it has not reached the published feeds this site
builds from.

So Phase 9C is built exactly as specified: **every feature below lights up when
its field is present and stays invisible when it is not.** Directions, calendar
files, favorites and the address-release rule need no new data and are live now.
Rating, contents, keywords, photo count and contact buttons will appear on the
first daily rebuild after Phase 9A's fields are published — no further website
change is needed. Both states are proven below.

## What was built

### 1. Sale pages (field-gated sections)

In `build.mjs`, `readSale` now parses the seven Phase 9 fields defensively
(cleaned, clipped, de-duplicated; a phone needs at least 7 digits, a company URL
must be http(s), a photo count must be a positive integer — anything else is
dropped, never shown half-parsed). `salePage` renders, only when present:

- **Rating badge with reasons** (`#dig-rating`, directly under the company
  line): `Deep Dig` / `Worth a Look` / `Slim Pickings` (any other value renders
  in a neutral badge), followed by every string in `ratingReasons`. The badge
  also appears in small form on sale cards and search results.
- **"What's there" section** (`#whats-there`, between When and the listing
  excerpt): the `contentsLine`, one chip per `photoKeywords` entry, and the
  photo count as **"N photos at the source"** linking to the first source
  listing, with the note that The Dig does not copy listing photos. No photo is
  ever republished — only the count and the link.
- **Contact the company** (`#contact-company`): a **Call** button
  (`tel:+1…` for 10-digit numbers) and a **Company page** button when
  `contactPhone` / `contactUrl` exist, with the published number shown under
  the buttons. The same values join the schema.org `organizer`, and keywords
  join the Event data as `keywords`.

### 2. Address rule

Full street address whenever the feed has it (unchanged). While held, the sale
page now leads with **"Address releases \<weekday\> 9:00 AM"** — the day before
the first session — above the city + ZIP (`releaseLabel` in `build.mjs`). Cards
carry the same line in short form ("Garland, TX 75041 · address releases
Thursday 9:00 AM"), as do the page description, the Event data and the calendar
files. The old "releases closer to the sale" wording is gone from sale pages
and cards.

### 3. Directions

Every sale page (a "Get directions" button in Where) and every sale card and
search result (a Directions link in a new card footer) links to
`https://www.google.com/maps/dir/?api=1&destination=…`. The destination is the
full street address when published; while held it is the published city/state/
ZIP, and the sale page says so ("Directions go to the general area until the
street address releases"). Cards were restructured so the link and the heart
sit outside the card's main link (no nested interactive elements).

### 4. Calendar

One `.ics` per sale day, generated at build time at
`/sale/<sale-id>/<YYYY-MM-DD>.ics`, linked as "Add to calendar" beside each row
of the When table (560 files in the current build). Sessions with both times
become timed events (converted to UTC from the city's zone with the build's
existing offset logic, so no VTIMEZONE is needed); a day without both times is
an all-day event with the listed hours in the description — no end time is ever
invented. Each file carries the address (or city + ZIP with the release line),
the contents line when present, the original-listing link, the sale-page link
and a confirm-before-you-travel note. Text is escaped and folded at 75 octets.

### 5. Search

`/search/data.json` records now carry `keywords`, `contentsLine` and
`digRating` when the feed has them (omitted otherwise, like `tags` before
them), and `prepare` in `static/assets/search.js` folds keywords and the
contents line into the matchable words, so a keyword matches the start of any
word in the title, company, categories, photo keywords or contents line. The
"what search covers" line on `/search/` now states this build's truth: today it
reads "Search covers listing titles and companies in this build. Photo keywords
and contents join the search automatically when the feeds carry them." — and
switches to naming the photo search (with the count of sales it covers) on the
first build that has the data. Search results also show the contents line and
rating badge when present.

### 6. Favorites (browser only)

New `static/assets/favorites.js`: hearts on every sale card, search result and
sale page ("Save as favorite" / "Saved as favorite") toggle a list of sale ids
in `localStorage` (`dig-favorites`). No account, no server; the sale page says
favorites stay in this browser. If the browser refuses the save, the heart
reverts and a visible warning is shown instead of pretending it saved.
`/search/` gains a **Favorites only** chip with a live count (also linkable as
`/search/?fav=1`); `find` in `search.js` takes an optional favorites list and
the page re-filters the moment a heart is tapped on the search page itself.

### 7. Daily rebuild, agents.txt / llms.txt, build.json

`.github/workflows/daily-rebuild.yml` is **untouched** (no diff in either
Phase 9C push) and still active; its last two runs before this work completed
successfully, and it already published the four-city rebuild this phase was
based on. `agents.txt`/`llms.txt` (one card, both files) now describe in plain
words: the full-address/release rule, the rating with reasons, contents line
and keyword chips, the photo count staying at the source, Call / Company page
buttons, Directions on every page and card, one `.ics` per sale day (with the
URL pattern), browser-only favorites with `&fav=1`, and the new search-record
fields with keyword matching over them. `build.json` gains an `enriched` block
counting sales per field plus calendar files, and `search.photoSearchSales` —
so "did the data land?" is answerable from the build summary alone. README
updated to match.

## Proof

### Tests (all in the repo, all passing after the final edit)

- `node test/preview.mjs` — fixture feeds now include a **fully enriched** sale
  (rating + reasons, keywords, contents, 38 photos, phone + company URL), a
  **partly enriched** one (rating/keywords/contents/photos, no contact) and a
  **plain held-address** one. It asserts each section renders exactly when its
  field exists, `tel:+15550101234` and the company URL appear only for the
  first, directions use the street address for one and the city + ZIP for the
  held one, "Address releases Thursday 9:00 AM" for a Friday-first sale, the
  day-one `.ics` is 15:00–21:00 UTC (9 AM–3 PM Central) with address + source
  link + contents line, a word only in `photoKeywords` ("brass") and a word
  only in `contentsLine` ("porcelain") each find their sale, the favorites
  filter narrows correctly (and returns nothing with no favorites), and
  `build.json` counts 2/2/1/2 enriched sales and 5 calendar files.
- `node test/check.mjs` — now also requires, on **every** build: a heart and a
  Directions link on every card and sale page; one valid folded VEVENT per
  session row; the weekday release line on held addresses; rating/What's-there
  sections matching each search record's fields in both directions; every
  keyword and contents word findable through the browser's own search code;
  the scope line matching the build; `enriched` counts matching the data; and
  the agent card naming each new feature. A regression in either direction
  (showing what the feed lacks, hiding what it has) fails the build before
  publish.
- `node test/favorites.mjs` (new) — runs `favorites.js` in Node against a
  minimal fake browser: stored hearts paint on load (including the sale-page
  label), clicks toggle, persist and announce, and a storage refusal warns
  visibly, keeps nothing and announces nothing.

### Real enriched data, end to end (local, not published)

A throwaway build against the local Phase 9A-enriched the-dig-data checkout
(feed URLs rewritten to `file:`, output to a temp folder; `docs/` untouched)
passed the full site check with **163 rated, 143 keyworded, 143 contents-lined,
138 contact-carrying and 156 photo-counted sales** out of 206. On the real
Houston sale `917efdb9740a5300` the page rendered: Deep Dig badge, "522 photos"
reason, contents line, keyword chips, "522 photos at the source", Call
(`tel:+18325672189`), company page, directions, heart and calendar links, and
its search record carried all ten keywords, the contents line and the rating.
This is the exact page the public site will serve for that sale once 9A
publishes; only the data differs.

## What happens next, automatically

Nothing here needs a second pass. When Phase 9A publishes the enriched feeds,
the next scheduled daily rebuild (11:37 UTC, unchanged) re-reads them and every
gated section, the photo-keyword search, and the scope line switch on by
themselves; `build.json`'s `enriched` counts will show it happened. The only
open item from the plan that touches display quality — a vision-model key for
true photo-content keywords — is a data-side decision; whatever the feeds
publish in these fields is what the site shows, word for word.
